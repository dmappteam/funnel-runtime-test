# Funnel Runtime

Мини-платформа для многошаговых веб-воронок. Экраны приходят с backend как JSON-конфиг, версии публикуются и откатываются без передеплоя, версия и A/B-вариант закрепляются за сессией, события принимаются собственным идемпотентным endpoint, дашборд считает воронку по уникальным сессиям.

| | |
| --- | --- |
| Воронка | https://firebrick-partridge-645250.hostingersite.com |
| Админка версий | https://firebrick-partridge-645250.hostingersite.com/admin |
| Дашборд | https://firebrick-partridge-645250.hostingersite.com/dashboard |
| Доступ к админке и дашборду | Basic Auth, логин и пароль переданы вместе со ссылкой |

На проде уже проиграны обе итерации: v1 → публикация v2 → публикация v3 → откат на v2. Активна v2, данные всех трёх версий в дашборде.

## Быстрый старт

Нужен Node.js 22 или новее.

```bash
npm ci
npm run dev
```

`npm run dev` поднимает API на http://localhost:3000 и фронтенд на http://localhost:5173 (Vite проксирует `/api`). База `data/funnel.db` создаётся сама, `configs/funnel-v1.json` публикуется как активная версия. Без `ADMIN_PASSWORD` внутренние страницы открыты, в логе будет предупреждение.

```bash
npm test                                  # 206 автотестов
npm run typecheck
npm run generate -- --sessions 120        # синтетический трафик в запущенный сервер
npm run demo                              # история первой итерации на чистой базе: v1, публикация v2
npm run generate -- --scenario iteration2 # вторая итерация: публикация v3, проверка, откат
```

Продакшен-сборка, один процесс отдаёт API и фронтенд:

```bash
npm run build
ADMIN_PASSWORD=secret npm start           # http://localhost:3000
```

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `PORT`, `HOST` | `3000`, `0.0.0.0` | адрес сервера |
| `DATABASE_PATH` | `data/funnel.db` | файл SQLite |
| `SEED_CONFIG` | `configs/funnel-v1.json` | версия, которую публикуем в пустую базу |
| `ADMIN_USER`, `ADMIN_PASSWORD` | `admin`, не задан | Basic Auth для `/admin`, `/dashboard`, `/api/admin`, `/api/analytics` |
| `WEB_DIST` | `apps/web/dist` | собранный фронтенд |

## Архитектура

```
packages/engine      логика воронки: схема конфига, условия, путь и прогресс, валидация, результат, проверка конфига, diff версий
packages/contracts   HTTP API, формат событий, построители событий, типы отчёта аналитики
packages/analytics   aggregate(): события → метрики дашборда, статистика A/B
apps/server          Fastify + SQLite: сессии, версии, приём событий, аналитика, раздача фронтенда
apps/web             React: воронка, админка, дашборд
apps/generator       генератор синтетического трафика и сверка с дашбордом
configs/             funnel-v1.json, funnel-v2.json, funnel-v3.json
```

Один движок используют все: фронтенд для навигации, сервер для результата и проверки ответов, генератор для симуляции. Фронтенд рендерит компонент по `step.type`, текстов и id шагов в коде нет.

Ключевые решения:

- **Конфиг сессии всегда берётся по закреплённой версии**, а не по активной. Поэтому сессия v2 в варианте B, стоящая на `tool_count`, доходит до конца после публикации v3, где этого шага в B нет.
- **Сервер источник правды** для сессии: версия, вариант, UTM, ответы. Клиент хранит только id сессии и очередь событий.
- **Создание сессии идемпотентно**: UUID генерирует клиент, `PUT /api/sessions/:id` создаёт сессию, только если её нет. Повтор после таймаута не даст второй сессии и второго `session_started`.
- **Конфиг проверяется до записи**: zod-схема и семантика (ссылки на шаги, ответы и варианты ответа, оператор совместим с типом вопроса, условие ссылается только на вопросы раньше по sequence в каждом варианте). Невалидный конфиг не может стать активным.
- **Каждая версия конфигов добавляет новый оператор** (`gte` в v2, `contains` в v3). Движок с первого дня поддерживает полный набор, поэтому вторая итерация не потребовала изменений кода.

## Модель данных

SQLite, схема в `apps/server/src/db/migrations.ts`, миграции применяются при старте.

| Таблица | Что хранит | Инварианты |
| --- | --- | --- |
| `funnel_versions` | конфиг версии как загружен, checksum, experiment_id | неизменяема, ключ `(funnel_id, version)` |
| `funnel_releases` | журнал `publish` / `rollback` | только дописывается. Активная версия = вершина стека после повтора журнала |
| `sessions` | закреплённые версия и вариант, способ назначения (`random` / `override`), UTM, состояние (ответы, текущий шаг, `rev`), результат, TTL | версия и вариант не меняются после создания |
| `events` | события с `event_id` как первичным ключом | версия, вариант, эксперимент, UTM копируются из сессии при приёме. Строка самодостаточна |
| `rejected_events` | отклонённые события с причиной | для отладки и метрик качества данных |

Новое событие, шаг, оператор или результат не требуют миграции: конфиг хранится как JSON, имя события текстом, свойства события JSON. Вторая итерация прошла без единой миграции.

## События

| Событие | Кто и когда | Свойства |
| --- | --- | --- |
| `session_started` | сервер, в транзакции создания сессии | |
| `step_viewed` | показ шага, в том числе после refresh и «Назад» | `step_type`, `visible_step_index`, `visible_step_count` |
| `answer_submitted` | валидный ответ на вопрос | `answer_kind` (тип ответа, не значение) |
| `step_completed` | переход вперёд с вопроса | `next_step_id` |
| `back_clicked` | возврат на предыдущий видимый шаг | `destination_step_id` |
| `result_viewed` | результат отрисован | `result_id` |
| `cta_clicked` | клик по основному CTA | `result_id`, `action` |
| `recommendation_expanded` | с v3: рекомендации раскрыты после CTA | `result_id`, `action`, `source` |

Базовые поля каждого события: `event_id`, `session_id`, `client_ts` и `server_ts`, `funnel_id`, `funnel_version`, `experiment_id`, `variant`, `step_id`, `utm_source`, `utm_medium`, `utm_campaign`.

Приём: `POST /api/events` с пачкой до 100 событий.

- Каждое событие проверяется отдельно, поэтому некорректное не ломает пачку. Ответ содержит статус каждого: `accepted`, `duplicate` или `rejected` с причиной.
- `INSERT … ON CONFLICT(event_id) DO NOTHING`: повтор того же `event_id`, в том числе всей пачки после таймаута, не создаёт дубль.
- Имя события проверяется по `events.allowed` **закреплённой версии сессии**. После отката с v3 на v2 сессия v3 продолжает слать `recommendation_expanded`, а сессиям v1 оно запрещено.
- Свойства режутся по whitelist из конфига, поэтому сырые ответы в аналитику не попадают, даже если клиент их пришлёт. Ответы живут только в состоянии сессии и стираются через сутки после истечения TTL.
- Клиент кладёт событие в outbox в `localStorage` до отправки, шлёт пачками, повторяет с backoff, при закрытии вкладки отправляет через `sendBeacon`.

## Правила агрегации

Все показатели считаются в уникальных сессиях. Каждая сессия сводится к множествам и максимумам, поэтому порядок прихода, дубли, возвраты назад и повторные просмотры не меняют счёт. Позиции шагов берутся из `stepSequence` конфига версии и варианта, а не из времени.

1. **Начали** = сессии с любым событием (обычно `session_started`).
2. **Дошли до шага** = у сессии есть событие на этом шаге, либо переход на него (`step_completed.next_step_id`, `back_clicked.destination_step_id`).
3. **Самый дальний шаг** = достигнутый шаг с максимальной позицией.
4. **Конверсия шага** = сессии, дошедшие до любого более позднего шага / дошедшие до шага. У условного шага свой знаменатель: remote-команды не создают ложный отвал на `office_days`.
5. **Отвал на шаге** = сессии, у которых это самый дальний шаг, и результат не показан. Ушедшие во время загрузки результата считаются отвалом на шаге результата, поэтому отвалы плюс сессии с результатом всегда равны числу дошедших до первого шага.
6. **Достижение результата** = `result_viewed` / начали. **CTR CTA** = `cta_clicked` / `result_viewed`. **Конверсия в CTA** = `cta_clicked` / начали.
7. **A/B сравнивается только внутри одной версии**: у каждой версии свой `experiment.id`. Override-сессии по умолчанию исключены.
8. **Дубли** отсекаются на приёме (первичный ключ) и повторно в агрегаторе.

## A/B-эксперимент

Эксперимент `question-order-and-result-framing`. Вариант назначается на сервере по весам 50/50 и сохраняется в сессии. Для проверки: `/?variant=B&reset=1`.

**Гипотеза (v1).** Вариант B начинает с лёгкого вопроса в один тап (`work_mode`), который сразу определяет ветку, а числовой ввод и множественный выбор переносит дальше. Вступление задаёт ожидание по времени («2-minute team check»). Результат подан как персональный вывод («Your team is ready to reduce meetings») вместо ярлыка («Async-native»), CTA конкретный («See the 30-day action list»). Мы ожидаем, что лёгкий старт снизит ранний отвал, а персональная подача повысит интерес к плану действий, и B даст больше кликов по CTA. В v2 и v3 B добавляет проблемную подачу («Is your team losing time…») и ставит `meeting_hours` вторым вопросом.

**Основная метрика:** конверсия в CTA, то есть доля сессий с `cta_clicked` от всех сессий варианта (intent-to-treat). CTR на экране результата для сравнения вариантов смещён: B меняет состав тех, кто доходит до результата.

**Вторичные метрики** частично разделяют два рычага: достижение результата отражает порядок вопросов и вступление, CTR отражает подачу результата. Guardrails: отвал на числовых шагах, доля возвратов назад.

**Мощность.** Для +5 п.п. при базе 20% нужно около 1 100 сессий на вариант (α = 0.05, мощность 80%). Дашборд показывает 95% доверительные интервалы, p-value и нужный объём выборки и прямо пишет, когда данных мало для вывода.

## Версии, откат и вторая итерация

- Публикация: `/admin` → загрузить JSON → Validate (ошибки, предупреждения, diff с активной версией) → Save and publish. Передеплой не нужен.
- Откат снимает текущую версию с вершины стека публикаций. Можно и явно активировать любую сохранённую версию кнопкой Publish.
- Новые сессии создаются только на активной версии. Начатые остаются на своей версии до конца TTL (72 часа с последней активности).

Вторая итерация (`funnel-v3.json`: ветка compliance, B без `tool_count`, событие `recommendation_expanded`) прошла без изменений кода и схемы. Конфиг v3 был в материалах с начала работы, поэтому новый оператор `contains` и отправку нового события (только если версия сессии его разрешает) заложили сразу. Новый конфиг с теми же возможностями публикуется так же, через `/admin`. Конфиг с незнакомым типом шага или оператором не пройдёт проверку при загрузке, и потребуется доработка движка. Генератор проигрывает вторую итерацию как сценарий и проверяет каждое утверждение:

| Проверка `iteration2` на проде | Итог |
| --- | --- |
| после публикации v3 новые сессии на v3 | 120/120 |
| начатые сессии v2 получают v2 и доходят до результата | 12/12 |
| вариант B v2 по-прежнему спрашивает `tool_count` | 6/6 |
| откат возвращает v2, новые сессии на v2 | 6/6 |
| сессии v3 после отката продолжают на v3 | 24/24 |
| их `recommendation_expanded` принимается | 17/17 |
| метрики дашборда совпадают с эталоном генератора | 53/53 |

## Генератор трафика

`npm run generate` ходит в настоящий HTTP API так же, как браузер: сервер сам назначает вариант, события собираются теми же билдерами, что во фронтенде.

- Пять UTM-профилей, варианты A и B, около 5% QA-сессий с override.
- Ответы покрывают все ветки и все результаты.
- Отвал на разных шагах, у B меньше ранний отвал и выше вероятность клика по CTA.
- Около 12% сессий возвращаются назад, около 10% перезагружают страницу.
- Около 8% пачек отправляются повторно с тем же payload, около 5% перемешиваются, часть задерживается и уходит после следующей. Около 1% событий заведомо битые.

В конце генератор печатает эталонные цифры, посчитанные по собственным записям симуляции (не через `@funnel/analytics`), и сверяет их с `GET /api/analytics`: начали, дошли до результата, кликнули CTA, дошли до каждого шага. Он же проверяет ответы приёма: `accepted` = уникальные события, `duplicate` = повторы, `rejected` = битые. Сверка точна на базе без посторонних посетителей: на проде во время прогона `demo` одна сессия пришла извне, и генератор честно показал расхождение на 1 в одном счётчике (59/60).

## Допущения и ограничения

- Сессия = единица рандомизации. Идентичности между устройствами нет.
- TTL 72 часа считается от последней активности. После истечения начинается новая сессия на активной версии с новым назначением варианта.
- Откат не переносит начатые сессии на старую версию: это прямо следует из требования о закреплении версии.
- Сравнение версий не является экспериментом: версии работали в разное время на разном трафике. Дашборд это подписывает.
- `client_ts` недоверенный и используется только для порядка внутри сессии.
- `answer_kind` содержит тип ответа (`single_select`, `multi_select`, `number`), а не его значение: в конфиге `storeRawAnswers: false`.
- Внутренние страницы защищены Basic Auth. Изменяющие запросы с чужих сайтов отклоняются по `Sec-Fetch-Site`, а в браузерах без него по `Origin`.
- Один процесс и SQLite достаточны для масштаба задания. Для роста: Postgres, очередь на приёме событий, предагрегации.
